# 构建指南

把一个能在飞牛上装的 `.fpk` 做出来：先 clone 一份 Alas，再攒出自带的 Python 运行时，最后装配打包。

> 本文里的路径都以**本仓库根目录**为基准。本仓库不含 Alas 源码，也不含任何构建产物。

---

## 前置条件

| 需要什么 | 说明 |
|---|---|
| Docker | 只用来构建 x86_64 运行时，`--platform linux/amd64`，arm64 的开发机也能出 x86 包 |
| `bash` / `python3` | 打包脚本用。没有 `rsync` 时：代码树回退到 tar 管道，运行时回退到 `cp -a` |
| `git` | 用来取 Alas 源码 |
| `fnpack` | 飞牛官方打包器，放到 `tools/fnpack` 并 `chmod +x`（第三方二进制，不入库）。本项目在 **1.2.3**（darwin-arm64）上验证通过 |

## 第 0 步：拿一份 Alas 源码

本仓库只放打包工程，Alas 本体在构建时临时取（体积太大，没必要进仓库）：

```bash
git clone --depth 1 --branch master \
  https://github.com/LmeSzinc/AzurLaneAutoScript ../alas
```

想要可复现的构建，就把版本钉死 —— 建议按 tag 或 commit 检出，并把用的版本记在 CHANGELOG 里：

```bash
git -C ../alas fetch --depth 1 origin <tag 或 commit>
git -C ../alas checkout <tag 或 commit>
```

`build_fpk.sh` 会按这个顺序找 Alas 源码：`--alas-src` 参数 → `$ALAS_SRC` 环境变量 →
同级 `../alas`、仓库内 `.alas/` → 上一层、上两层、上三层目录（开发时本工程可能嵌在
Alas 仓库里）。哪个候选下有 `alas.py` + `module/` + `deploy/` 就算命中；
全都没有就直接报错并提示上面这条 clone 命令。

### 顺便钉住「在线更新的基准版本」

打包时脚本会算出一个**上游基线 commit** 写进包里的 `alas_version.json`：

```bash
git -C <alas-src> merge-base HEAD refs/remotes/origin/master    # 脚本自动执行
```

它是「安装后 Alas 界面上显示的当前版本」，也是判断「有没有新版本」的比对基准。
想手动指定就设 `ALAS_COMMIT=<sha>`。

⚠️ **别拿你自己 checkout 的 HEAD 当基准。** 如果你在 Alas 源码上打了本地提交，
HEAD 和上游 master 不是一个东西，安装后会**永远显示「有新版本」**。脚本用 `merge-base`
正是为了规避这点。包里的 `dirty` 字段同理 —— 它只统计**核心源码路径**
（`alas.py gui.py module campaign deploy assets bin submodule webapp requirements*.txt`，
排除 `deploy/fnos`），因为根目录 `.gitignore` 之类的无关改动会造成误报。

## 第 1 步：构建自带的 Python 运行时

```bash
./runtime/build.sh        # 输出 runtime/dist/runtime（约 703 MB，首次较慢）
./runtime/smoke.sh        # 冒烟测试：挂到 /opt/alas-rt 验证自包含
```

`build.sh` 以 `python:3.7-slim-bookworm` 为底装上 Alas 的依赖，再用 `collect.sh`
把 CPython 前缀整理成一棵**可重定位**的树：

```
runtime/dist/runtime/
├── bin/python3.7            # 入口（python3 是指向它的软链）
└── lib/
    ├── python3.7/{stdlib,lib-dynload,site-packages}
    ├── libpython3.7m.so.1.0
    └── *.so*                # libssl / libcrypto / libsqlite3 / libffi / libz / libgomp …
```

规矩是：**glibc、ld-linux 这类基线库由飞牛系统提供，其余全部随包带走**。
启动时靠 `LD_LIBRARY_PATH=<runtime>/lib` 生效，所以不需要 patchelf，也不依赖飞牛提供什么库。

> ⚠️ **这棵运行时里没有系统 CA 目录**（`/etc/ssl/certs` 不在包内），只有
> `lib/python3.7/site-packages/certifi/cacert.pem`。而标准库 `urllib` **不读 certifi** ——
> 所以包内**任何 HTTPS 请求都必须显式用 certifi 建 `SSLContext`**，否则在缺 CA 的机器上
> 会一律以证书错误失败。更新补丁里的 `_ssl_context()` 就是干这个的（见「更新补丁是怎么工作的」）。

`smoke.sh` 会把运行时挂到 `/opt/alas-rt`（和构建路径毫无关系），在干净的
`debian:bookworm-slim` 里导入 `numpy / cv2 / mxnet / scipy / matplotlib / PIL` 以及
`lz4 / msgpack / zmq / gevent / cffi / yaml / psutil`，并断言 `av` **不存在**。

### 依赖清单做了四处 Linux 适配

Alas 上游的 `requirements.txt` 是 Windows 上生成的平铺清单，构建期做了这四处改动
（详见 `runtime/Dockerfile` 注释，与上游 `deploy/docker/requirements_generator.py` 同口径）：

| 改动 | 为什么 |
|---|---|
| `pywin32` 补 `sys_platform == "win32"` 标记 | Linux 上没有任何分发，会中断安装 |
| 移除 `alas-webapp` | Windows 专用的 Electron 外壳，内置 24 MB `app.asar` |
| 移除 `av` | PyPI 上只有 sdist（没有 cp37 的 Linux 轮子），会连带拉进整个 FFmpeg 闭包；它只在 scrcpy 截图路径里被懒加载 |
| `opencv-python` → `-headless` | 去掉 libGL / libX11 / libgtk 依赖 |

安装时必须用旧解析器（`--use-deprecated=legacy-resolver`）：该清单本身不自洽
（`requests==2.18.4` 与 mxnet 要求的 `requests>=2.20.0` 矛盾），但传递依赖已经全部钉死，
按原样装即可。

## 第 2 步：装配并打包

```bash
./build_fpk.sh              # 校验 → 清理 → 骨架预检 → 装配 → 校验 → 打包
./build_fpk.sh --assemble   # 只装配，不打包
./build_fpk.sh --skip-alas  # 调试用，跳过 Alas 源码复制
```

产物：`dist/alas-fnos_<version>.fpk`（装配约 859 MB → 包约 344 MB）。

`--alas-src` 指向另一份 Alas 检出，用于「用历史版本打包」这类测试：

```bash
./build_fpk.sh --alas-src ../alas-old
```

版本记录会从**该检出自己的 git** 推断（`merge-base HEAD origin/master`），
所以用旧版本检出打出来的包，`alas_version.json` 自动就是旧版本，不必手写 `ALAS_COMMIT`。

流程顺序**不可调换**，两个关键点：

1. **骨架预检必须在装配前跑。** 装配后再跑扫描器，会把捆绑的 CPython 标准库、
   site-packages 和 Alas 自带脚本一起扫进去，报出大量与交付无关的误报。
   （预检脚本随仓库分发在 `tools/validate_fnos_project.py`，构建脚本会优先用它；
   找不到时会**明确报警并跳过**，可用 `VALIDATOR=<path>` 指定。）
2. **向导文件不能是空数组。** 见下面的[平台注意事项](#平台注意事项)。

### 想验证「检测更新 + 更新」功能，得专门打个测试包

正式包的基线就是上游最新，装上去点「检查更新」只会显示「已是最新」，**走不到更新流程**。
要验证更新功能，得打一个**基线落后于上游**的包：

```bash
# 1) 取上一个上游版本（--shared 走本地对象库，秒级完成，不复制 700 MB）
OLD="$(git -C ../alas rev-parse refs/remotes/origin/master^1)"
git clone --shared --no-checkout ../alas ../alas-old
git -C ../alas-old checkout --detach "$OLD"
git -C ../alas-old update-ref refs/remotes/origin/master \
    "$(git -C ../alas rev-parse refs/remotes/origin/master)"

# 2) 抬高应用版本号（设备上已有同版本时装不上去）
sed -i.bak 's/^version=.*/version=<比现有高的版本>/' fnos-app/manifest

# 3) 打包
./build_fpk.sh --alas-src ../alas-old

# 4) 还原 + 清理
mv fnos-app/manifest.bak fnos-app/manifest
rm -rf ../alas-old
```

装到设备后：更新面板的「当前版本」应显示旧 SHA → 点「检查更新」提示有新版本 →
点「立即更新」应下载并自动重启 → 版本记录 `source` 变 `"update"`，
配置和日志不丢、安装目录不被改动。

⚠️ 测试包版本比正式包高，**无法直接降级**：测完要先在应用中心卸载（默认保留数据），
再装正式包。

### 更新补丁是怎么工作的

`fnos-app/patch/` 下两个文件，装配后落在包内 `<target>/patch/`：

| 文件 | 作用 |
|---|---|
| `sitecustomize.py` | CPython 启动时由 `site` 模块**自动导入**；把自身目录塞进 `sys.path` 并调用 `alas_fnos.install()`。整个过程包在 try/except 里，出错只写 stderr |
| `alas_fnos.py` | 真正干活的：注册 import hook 接管 `module.webui.updater`，替换 `Updater` 的三个方法 |

`console_server` 启动 Alas 时这样注入：

```python
env["ALAS_FNOS_PKGVAR"] = <TRIM_PKGVAR>
env["ALAS_FNOS_APPDEST"] = <TRIM_APPDEST>
env["PYTHONPATH"] = <TRIM_APPDEST>/patch
cmd = [<runtime>/bin/python3.7, <TRIM_PKGVAR>/alas/gui.py, "--host", "127.0.0.1", "-p", "22267"]
```

被替换的三个方法（上游原本全部依赖 `git`）：

| 上游方法 | 补丁实现 | 依赖 |
|---|---|---|
| `Updater.get_commit` | 读 `alas_version.json` / 上游版本缓存（`origin/*` 时查 GitHub API 拿历史） | 无 git |
| `Updater._check_update` | 版本真值取**官方提交列表的第一行**（与面板下方「详细提交历史」同源），与本地基准比对 | 无 git |
| `Updater.git_install` | 下载源码包 tarball → 校验 → `os.replace` **原子交换** `$TRIM_PKGVAR/alas` | 无 git |

外层方法（`run_update` / `update` / `pip_install` / `check_update`）一律不动，
所以上游的按钮、进度提示、`EnableReload` 触发的自动重启全部原样生效。

几处容易踩的实现细节（1.0.4 起陆续定稿；「版本真值来源」那条是 1.2.1 才改的）：

| 细节 | 做法 | 为什么 |
|---|---|---|
| 检查更新的**三态** | `True` 有更新 / `False` 已是最新 / **`"failed"` 检查失败** | 上游失败时也返回 `0`（= 无更新），"查不到"会被显示成"不用更新"，最难查 |
| 检查期间的状态 | 先置 `self.state = "checking"` | 与上游一致，面板会显示 loading |
| HTTPS 证书 | `_ssl_context()` 用 `certifi.where()` 建上下文 | 包内运行时没有系统 CA（见第 1 步） |
| 版本真值来源 | 官方 `api.github.com/.../commits` 的第一行；不可达时才按 `LATEST_URLS` **顺序**回退镜像 | 与「详细提交历史」同源，不会出现「上游显示旧版本、历史里却有新提交」的自相矛盾 |
| 探测端点 | 5 个，`_parse_latest()` 兼容 GOC 与 GitHub 两种响应形状 | 官方接口不可达时仍能判断是否有更新 |
| ⚠️ **不要改成并发抢答** | 顺序即优先级，串行取第一个可用 | 2026-10-05 实测：GOC COS 0.18 s 但停在 `77f4d01f`，123clouddisk 0.20 s 且已是 `b9a965c`。只快 20 ms 的过期源会把正确版本顶掉，面板于是显示「已是最新」 |
| 本地版本读不到时 | `read_version()` 回退到出厂记录 `<target>/alas_version.json` | 面板不显示空白版本，便于定位问题 |

**为什么不直接改 Alas 源码**：`$TRIM_PKGVAR/alas` 会被更新整体替换，写进源码树的改动下次更新就没了。
补丁放在 `<target>/patch/`（不参与更新），所以**补丁不会随 Alas 更新失效** —— 这是整个方案能成立的关键。

**写补丁时的硬约束**：

- 只用标准库，且必须是 **Python 3.7 可解析的语法**（包内运行时就是 3.7）。
  提交前用 `ast.parse(src, feature_version=(3,7))` 自检一次。
- 补丁自身**绝不能抛异常**拖垮 Alas 启动 —— 所有入口都要 try/except。
- 替换方法时用 `_alas_fnos_patched` 之类的标记保证幂等（同一个进程可能多次进入）。

**已知限制（改不掉的）**：依赖不会跟着更新。`site-packages` 是打包时冻结的，
`InstallDependencies` 强制 `false`；上游新版若引入新依赖，更新后 Alas 会 `ImportError`。
逃生通道是 `POST /app/alas-fnos/api/alas/reset`（回到出厂版本，源码树和依赖一起回退）。

### 装完新包「看起来没生效」怎么查

先分清**两件事**：数据（`$TRIM_PKGVAR`）有没有被删，和界面显示什么，**没有因果关系**。
只要升级后应用**重启过**，`console_server` 启动时的 `prepare()` 就会比对
「包内 `alas_version.json`」与「运行期 `alas_version.json`」：不一致就重播源码树并刷新记录。

一键排查（只读，自动从运行进程的 `/proc/<pid>/environ` 取路径）：

```bash
bash tools/diagnose-update.sh
```

| 现象 | 含义 |
|---|---|
| Alas 日志里**有** `[alas-fnos] …` 行 | 补丁生效 |
| 一行都没有 | 补丁没生效 → 查 `PYTHONPATH` / `<target>/patch/` / `console.log` 里的启动命令 |
| 「本地」版本 = 升级前的旧值 | 跑的还是旧进程 → 升级后没有重启（`cmd/upgrade_*` 已负责，见「平台注意事项」） |
| 「上游」为空且状态是「更新失败」 | 探测不到上游：网络或证书（先看 `diagnose-update.sh` 第 5 段） |
| 「本地」为空 | 两份版本记录都读不到 → 看 `console.log` 里的播种决策那两行 |

## 软件包结构

装配完成后，fpk 里是这样：

```
manifest  ICON.PNG  ICON_256.PNG
cmd/  config/  wizard/
app.tgz → alas/  bin/  config/  patch/  runtime/  server/  ui/  alas_version.json
```

本应用**不自带前端**：没有 `console/`，`console_server` 只保留控制面 API 与 PyWebIO 反代，
其余路径一律 308 到 `/app/alas-fnos/alas/`。

`app.tgz` 里三个容易忽略的条目：

- `bin/adb` —— 包内自带的 adb（来自 `vendor/adb/`，见下节）
- `patch/` —— 更新补丁（见上一节），位于 target 内，**不随 Alas 更新失效**
- `alas_version.json` —— 出厂版本记录，`source: "fpk"`。首次启动时被复制到
  `$TRIM_PKGVAR/alas_version.json` 作为运行基准；界面里更新成功后会改写成 `source: "update"`

### 包内自带 adb

`vendor/adb/` 收录 platform-tools 的 Linux x86_64 `adb`（原样分发，`NOTICE.txt` 与
来源/SHA256 记录都在同目录）。装配落到 `<target>/bin/adb`，`console_server` 启动 Alas 时
做三件事，让用户**零配置**：

1. `<appdest>/bin` 前插进 gui.py 的 `PATH` → 默认 `AdbExecutable=adb` 直接命中；
2. **保证可写 `HOME`**，优先级 `$TRIM_PKGHOME` → `<appdest>/home` → `$PKGVAR/home` ——
   adb server 首启要写 `~/.android/adbkey`，平台默认 HOME 不可写会让 `adb start-server`
   **静默失败**（stderr 被调用方吞掉），表面症状只是 5037 `Connection refused`，极难定位；
3. 起 gui.py 前 best-effort 预启动一次 `adb start-server`（失败不阻塞）。

换 adb 版本 = 替换 `vendor/adb/adb`（连同 NOTICE/README 的版本与校验和）后重打包。

`manifest` 里几个不能改的值：

```ini
appname=alas-fnos                  # 决定网关前缀 /app/alas-fnos（由 console_server 按 appname 推导）
platform=x86                      # 运行时是 x86_64 ELF，必须 x86
desktop_uidir=ui
desktop_applaunchname=alas-fnos.main
micro_app=true
disable_authorization_path=true
checkport=false
ctl_stop=true
```

`fnpack build` 自己会写 `checksum`（`app.tgz` 的 md5），不用手填。

## 运行期加固（1.2.1 起）

这一节是 `console_server.py` 与 `cmd/main` 在「7x24 挂机」这个前提下加的防护。
全部只在自己这一层，不碰上游 Alas 一行代码。

### 反代前校验 22267 的监听者身份

**要解决的问题**：`console_server` 原本只检查 `127.0.0.1:22267` 通不通，通就转发。
如果这个端口被**别的进程**占着（最典型的是以前用 root 手工跑过一次 `python gui.py`、
它一直没退），新包的 `gui.py` 会 bind 失败，而健康检查照样「通过」——
网关于是把浏览器请求全部反代给那个老进程。用户看到的是**老代码渲染的旧界面 + 旧版本号**，
还会以为「重装没生效、配置还在」，极难定位。真机上确实踩过（[HANDOFF](HANDOFF.md) 4.12.8）。

**做法**（`Context.listener_owner()`）：判定顺序有意从「不需要权限就能拿到」的信息开始。

1. 读 `/proc/net/tcp{,6}`，取该端口 **LISTEN** 条目的 socket **uid**。这个字段属于
   socket 而不是进程，所以**即使占用者以 root 运行、我们无权读它的 `/proc/<pid>`，
   也能一眼判出「这不是我的」**—— 正是上面那个场景。
2. uid 与本进程相同，才去扫 `/proc/*/fd` 定位持有该 inode 的 pid，再校验它的
   `cmdline` / `cwd` 是否属于本包（`cwd` 带 `(deleted)` 说明源码树已被换掉或卸载）。

返回四态，**只有 `foreign` 才拦**：`ours` / `foreign` / `none` / `unknown`。
`unknown`（读不到 `/proc`，或同 uid 但定位不到进程）**一律放行** ——
宁可漏判一次，也不能让探针把正常服务掐了。判定结果缓存 5 s（反代是热路径），
拒绝日志按 key 限流 120 s，避免刷屏。

| 出口 | 命中 `foreign` 时的行为 |
|---|---|
| HTTP 反代 | 503 + 一页中文说明（不是裸 JSON，用户能看懂） |
| WebSocket 反代 | 关闭码 1011 |
| 启动 Alas | 拒绝启动并在 `console.log` 写明占用者，不再拉起一个注定 bind 失败的进程 |
| `/api/status` | `state` 报 `conflict`，并带 `detail` |

> 改这块时务必守住「判不出来就放行」这个不变式。历史问题全都源于「健康检查太乐观」，
> 不要用另一个过于自信的探针去修它。

### 日志封顶

`alas.log`（含 uvicorn 的每请求 access log）和 `console.log` 都只追加，上游 Alas 的
`log/*.txt` 也是一天一份只增不减。7x24 跑下去会把数据目录吃满，所以：

| 对象 | 策略 | 常量位置 |
|---|---|---|
| `alas.log` | 启动前超过 16 MB 滚成 `alas.log.1`（只留一代，占用上界 ≈ 2×） | `console_server.py` 的 `LOG_ROTATE_BYTES` |
| `console.log` | 同上 | `cmd/main` 的 `CONSOLE_LOG_MAX_BYTES` |
| `$TRIM_PKGVAR/log`（Alas 自己的任务日志） | 总量超过 512 MB 时从**最旧**的开始删，逐条留痕 | `console_server.py` 的 `ALAS_LOG_MAX_MB`；环境变量 `ALAS_FNOS_LOG_MAX_MB` 可覆盖（设 `0` 关闭） |

⚠️ `ALAS_FNOS_LOG_MAX_MB` 只是**运维/调试开关**：飞牛只给应用注入平台自己的环境变量
（[官方环境变量清单](https://developer.fnnas.com/docs/core-concepts/environment-variables/)），
没有给用户自定义环境变量的入口。真要长期改这个上限，得在 `cmd/main` 里 `export`，
或者改上面两个常量后重打包。

> 顺带一个**踩过的坑**：`rotate_console_log()` 里读文件大小必须 `tr -d '[:space:]'`。
> BSD/macOS 的 `wc -c` 会输出前导空格，直接丢给 `case ... *[!0-9]*` 会被当成非数字，
> 于是阈值判定永远不成立、轮转**静默失效**（Linux 的 GNU `wc` 没这个问题，所以只在本机测才暴露）。

### PID 归属校验

`read_pid()` 一直把进程启动时间一起写进 PID 文件，但从没拿它校验过。PID 被系统回收后，
`os.killpg(os.getpgid(pid), SIGTERM)` 砍的是**无关进程的整个进程组**。
现在 `console_server` 与 `cmd/main` 动手前都会先看 `/proc/<pid>/cmdline` 是否含本包路径：

| 判定 | 行为 |
|---|---|
| 确认是本应用 | 照常发信号 |
| 确认不是（PID 复用） | **不发任何信号**，只清理 PID 文件并打日志 |
| 读不到 `/proc`（判不出来） | 按原逻辑继续 —— 不能因为探针读不到就误判成「没在运行」，那会漏掉升级后的重启（[HANDOFF](HANDOFF.md) R20） |

### 尾部读日志

`/api/log` 原先是 `deque(f, maxlen=n)`：内存有界，但**磁盘 I/O 是 O(文件大小)**。
现在从文件尾 seek 往回读，2.8 MB 的日志实测 **2,800,012 B → 8,192 B（342×）**，
差距随日志增大线性拉大。

### 改完先跑自测

这两个脚本**不需要飞牛、不需要 Linux**：监听者判定那部分靠一棵**假的 `/proc` 树**
（假 `net/tcp` + 假 `cmdline`/`cwd`）把 Linux 才走的分支喂出来，所以在 macOS 开发机上就能跑。

```bash
python3 tools/selftest-console_server.py    # 45 项：轮转 / 尾读 / 监听者四态 / 反代路径 / 拒绝页
bash    tools/selftest-cmd-main.sh          # 16 项：pid_is_ours 三态 / read_live_pid / 信号护栏
```

真机上仍需复测（`/proc` 只有真机才有）：**故意让另一个 uid 占住 22267 再启动应用**，
应看到 503 说明页而不是被转发；`alas.log` 超阈值后重启应出现 `.1`。

## 平台注意事项

打包时踩出来的、值得记一笔的几条：

- **`wizard/upgrade` 和 `wizard/uninstall` 不能是空数组 `[]`。** 留空的话真机安装会在
  `Verifying files...` 之后失败，设备 CLI 只显示 `code 10111`，日志里是
  `APP_INSTALL_FAILED_PKG_EXCEPTION`，而且根本不会发起安装。规则边界（逐文件实测）：
  `upgrade` 空 → 失败、`uninstall` 空 → 失败、`config` 空 → 通过、`install` 有内容 → 通过。
  **不需要的向导文件就别创建**，别留个空数组。`build_fpk.sh` 里加了防回归校验。
  （本包目前只有 `wizard/install` 和 `wizard/uninstall` 两个文件，都有内容；
  `wizard/upgrade`、`wizard/config` **不创建**。）
- **向导里的自定义字段必须用 `wizard_` 前缀，且不能用 `TRIM_`**（平台保留前缀）。
  `field` 名会成为生命周期脚本的**同名环境变量** —— 卸载向导里的
  `"field": "wizard_data_action"` 对应脚本里的 `$wizard_data_action`。
  字段缺失时脚本一律按保守分支走（本包卸载默认**保留数据**）。
- **卸载时不要整目录 `rm -rf $TRIM_PKGVAR`。** 平台可能往那个目录放自己的东西，
  只删本应用自己管理的条目（`config/`、`log/`、`alas/`、`*.pid`、`alas_version.json`、
  `.alas-prev-*` 等），并且先做**路径护栏**（拒绝 `""` / `/` / `/var` / `/usr` / `/vol*`）。
  两个卸载脚本（`init` 主责 + `callback` 兜底）都实现同一套逻辑，`init` 被打断时 `callback` 还能兜住。
- **`fnpack build` 有两条强制校验**（构建期直接失败）：`app/ui/config` 的条目名必须以
  `appname` 开头；`desktop_applaunchname` 必须与某个条目名完全一致。
- **`$TMPDIR` 残留会引发假失败**（`Copy pack ... is a directory`），与包内容无关。
  脚本已为每次构建准备私有 `TMPDIR`，但残渣还是会攒：实测在 `$TMPDIR` 里发现过
  **972 MB** 的 `fnpack*` 旧目录（不是脚本自己那份，已经没人管了）。
  构建莫名变慢、或磁盘吃紧时先看一眼：

  ```bash
  du -sh "${TMPDIR:-/tmp}"/fnpack* 2>/dev/null
  rm -rf "${TMPDIR:-/tmp}"/fnpack*          # 确认只有构建残渣后再删
  ```
- **`cmd/main` 的 `status` 未运行时必须 `exit 3`**，未知参数 `exit 1` —— 打包器和校验器都认这个。
- **生命周期脚本不要依赖控制面 API**：`/api/*` 要求网关注入的 `X-Trim-*` 首部，
  脚本本地调用只会拿到 403，停服务请直接按 PID / 进程组处理。
- **`$VAR` 后面紧跟中文时必须写 `${VAR}`。** macOS 自带 **bash 3.2.57**，在 UTF-8 环境下会把
  多字节字符的前导字节当成变量名的一部分：`echo "$FOO，"` 会被解析为变量 `FOO\xef`，
  在 `set -u` 下直接报 `unbound variable` 并退出。这类写法**多半藏在报错分支里**，
  平时不触发、真出事时才炸 —— 写脚本时统一加花括号最省事。
  改完扫一遍可执行行（注释和二进制不参与，`tools/fnpack` 就是二进制）：

  ```bash
  python3 - <<'PY'
  import os, re, stat
  pat = re.compile(rb'\$[A-Za-z_][A-Za-z0-9_]*[\x80-\xff]')
  hits = 0
  for root, dirs, files in os.walk('.'):
      if any(p in root for p in ('/.git', '/app/', '/dist', '/vendor', '/runtime/dist', '/.trae')):
          continue
      for name in files:
          p = os.path.join(root, name)
          if not os.stat(p).st_mode & stat.S_IXUSR:
              continue
          raw = open(p, 'rb').read()
          if b'\x00' in raw[:4096]:          # 二进制（fnpack 等）直接跳过
              continue
          for m in pat.finditer(raw):
              line = raw[raw.rfind(b'\n', 0, m.start()) + 1:raw.find(b'\n', m.start())]
              if line.lstrip().startswith(b'#'):
                  continue
              hits += 1
              print('%s:%d %s' % (p, raw[:m.start()].count(b'\n') + 1,
                                  line.decode('utf-8', 'replace')[:100]))
  print('命中 %d 处（0 = 干净）' % hits)
  PY
  ```
- **给子进程注入 PATH 只解决「找到二进制」。** 凡是自身要写状态目录的工具都必须
  一并保证 `$HOME` 可写：adb 的 `~/.android`、git 的 `~/.gitconfig` 等。真机实测：
  平台拉起的进程 HOME 不可写时，`adb start-server` 会**静默失败**（stderr 被调用方
  捕获），表面症状只是 5037 `Connection refused`，极难定位。
- **升级要自己负责把应用重启到新代码上。** 平台会把 `<target>` 下的文件整体替换掉，
  但**不保证**替换后把应用拉起来；旧进程继续跑就等于还在用旧代码（表现为「装了新包却还是旧行为」，
  例如更新面板还显示上一版的版本号）。本包的做法是成对的两个脚本：
  `cmd/upgrade_init` 在替换前用 `cmd/main status` **记下应用是否在运行**
  （`$TRIM_PKGVAR/.upgrade-restart-pending`），`cmd/upgrade_callback` 在替换后看到标记就
  `stop` → `setsid start`。这样既不强行拉起用户本来就关着的应用，也能保证跑的是新代码。
